# ANSWER — Staff-level review of `main` (d612e0b)

Line numbers refer to `HEAD`. `[AI]` marks a typical old-AI-generated smell. `[V]` marks a finding I verified by running something (see the notes at the end).

## Critical

1. **`main` does not build from a clean clone.** `[V][AI]` `.gitignore:8` has `storage/`. On this case-insensitive checkout (`core.ignorecase=true`) it swallowed `src/NetDropbox.Infrastructure/Storage/`, so `LocalBlobStorage`, `S3CompatibleBlobStorage` and `FileSystemChunkStorage` are **not in git** (`git ls-files` has 0 files there; `git check-ignore -v` names `.gitignore:8`). `DependencyInjection.cs:31,45,52` references them. The CI in `ci.yml:16-18` would fail on the first run, yet the README (`README.md:16`) advertises CI. **Prod impact:** you can't deploy what's in source control, and the image `Dockerfile:3` builds from would come from someone's laptop.
2. **The EF model fails to initialize, so every DB call throws.** `[V]` `NetDropboxDbContext.cs:44` `HasMany<FileVersion>("_versions")` together with `b.Navigation(x => x.Versions)` (`:48`) raises `InvalidOperationException: The member 'FileNode._versions' cannot use field '_versions' because it is already used by 'FileNode.Versions'`. In Development, `DbSeeder` (`Program.cs:85`) crashes startup. In any other environment, the first request 500s. The README describes a working product. `[AI]`
3. **Copy launders quarantined files.** `FileService.CopyAsync` (`FileService.cs:76`) calls `copy.MarkScanClean(...)` unconditionally. Copying an `Infected` or `PendingScan` file creates a `Clean` copy that downloads and public-shares normally. That's a malware-distribution path. (Copy also skips the quota reservation and never checks that `parentId` is the caller's own folder.)
4. **Download by `versionId` skips the scan gate.** `OpenDownloadAsync` (`FileService.cs:118-120`) checks `node.ScanStatus` (the *current* version) and then serves any `versionId` of that node. Upload infected v1 (quarantined), upload clean v2, then `GET /download?versionId=v1` serves the infected bytes. Root cause: scan state lives on the node, but content lives on the version.
5. **JWT signing key falls back silently to a public constant.** `[AI]` `Program.cs:42` and `AuthController.cs:32` use `?? "local-development-signing-key-change-me-32chars"`. The same value is committed in `appsettings.json:8`, `.env.example:5` and `docker-compose.yml:60`. A missing or renamed config key means anyone can forge tokens for any `nameid` (`CurrentUser.cs:9-11`). Secrets must fail closed. (INC-005 is built on this.)

## High

6. **Dual write DB → in-memory queue loses work.** `CompleteUpload.cs:82-84`: `SaveChanges`, then delete chunks, then `EnqueueAsync` into an unbounded in-process `Channel` (`ChannelProcessingQueue.cs:8`). A crash or deploy between commit and enqueue, or any time before the worker drains, leaves the file `PendingScan` **forever**. Nobody reads `processing_jobs` back, so it's write-only bookkeeping. `[AI]` Redis and RabbitMQ are provisioned in `docker-compose.yml:18-30` and listed in the README, but no code uses them. It's a fake integration.
7. **One exception in the worker stops the whole API.** `ProcessingWorker.cs:32-34` (lookups) and `:72` (the `SaveChanges` inside `catch`) run outside any handler. An exception escapes `ExecuteAsync`, and .NET 8's default `BackgroundServiceExceptionBehavior.StopHost` shuts the process down. A Postgres blip during a scan takes down upload and download too. The worker and the API share one process.
8. **Restore-version bricks the file.** `FileNode.RestoreVersion` (`FileNode.cs:68`) sets `PendingScan`, but `FileService.RestoreVersionAsync` (`FileService.cs:106-112`) never queues a scan job. The file can't be downloaded again (`EnsureDownloadable`, 409).
9. **Double `complete` → duplicate versions and a double quota charge.** `CompleteUpload.cs:33` checks `session.Status == Open` with no lock. `UploadSession` has no concurrency token, so two concurrent completes (a client retry on timeout, since hashing large files is slow) both pass. The result is two `FileVersion`s, `AddReference` twice, and `Reserve` twice. The same check-then-act pattern creates duplicate `FileNode`s with the same name (`:63-72`; the index at `NetDropboxDbContext.cs:38` is **not unique**).
10. **The optimistic concurrency tokens are inert.** `[V][AI]` `Entity.Version` (`Entity.cs:8`) is mapped as `IsConcurrencyToken()` on a plain `bigint` column (`ValueGenerated=Never`) that no code increments. Every UPDATE matches `WHERE "Version" = 0`. So `UsedBytes`, `RefCount` and `AccessCount` all lose updates under concurrency. The config *looks* like protection. Fix: `IsRowVersion()` → Npgsql maps it to `xmin`, or use conditional SQL updates.
11. **Storage accounting only goes up.** `UserStorageAccount.Release` and `BlobObject.RemoveReference` have **zero callers**. Deleting and then purging (`JanitorWorker.cs:46-51`) never frees quota and never decrements refcounts. Blob files are never garbage-collected. The README's "reference counts" (`README.md:11`) are half a feature. `[AI]`
12. **The public share link ignores trash.** `ShareService.OpenPublicDownloadAsync` (`ShareService.cs:62`) loads the node without `!IsDeleted`. Trashing a file doesn't stop its public link. Users expect trash to stop sharing. A link to a **folder** 500s on `Versions.Single(x => x.Id == null)` (`:64`).
13. **Folder operations don't cascade, and there are no FKs.** `MarkDeleted` (`FileNode.cs:72-77`) flags only the folder. Children stay searchable and downloadable. The janitor hard-deletes the folder and orphans the children. `[V]` The model has exactly one FK (FileVersion → FileNode). `ParentId`, `ShareLink.FileNodeId`, `DirectShare.*` and `UploadChunk.UploadSessionId` have no referential integrity.
14. **A folder can be moved into itself.** `FileNode.Move` (`FileNode.cs:46`) guards only `Type == File`, and `MoveAsync` doesn't check ancestry (`FileService.cs:52-62`). Moving F into F or into its descendant detaches the subtree from the root.
15. **An upload chunk is written before it's verified.** `UploadChunk.cs:40-42` `StoreAsync` does `File.Create` on the *final* chunk path, then compares the checksum. A bad retry of an accepted index overwrites good bytes. The DB still says the index is uploaded, so the client never resends it, and `complete` fails with a checksum mismatch forever. Concurrent PUTs to the same index hit an `IOException` sharing violation, which becomes a 500. (The uncommitted Astra change fixes this. Compare your fix with it.)
16. **The blob is saved before the DB and quota decisions.** `CompleteUpload.cs:54` writes to blob storage before `user.Reserve` (`:80`) can throw and before the unique `ContentHash` insert (`NetDropboxDbContext.cs:62`) can conflict. Two users completing the same new content race into a unique violation (500). Quota failure leaves an orphan blob. The ordering and compensation are undefined.

## Medium

17. **Search is a sequential scan over up to 1 MB of text per row.** `FileService.cs:129` uses `Name.ToLower().Contains` and `ExtractedText.ToLower().Contains`. There's no trigram or tsvector index, and `skip` is unbounded (a negative value becomes a Postgres error, so a 500).
18. **Upload status leaks the query into the controller and returns 500.** `UploadsController.cs:24-29` injects `IAppDbContext` into the API layer. `SingleAsync` on another user's session throws `InvalidOperationException`, which surfaces as a 500 instead of a 404.
19. **Duplicate direct share returns 500, and roles are never enforced.** A unique index (`NetDropboxDbContext.cs:96`) meets an unhandled `DbUpdateException`. `DirectShareRole` is stored but read nowhere. A share recipient can list the file (`SharedWithMeAsync`) but can't download it (owner-only). The feature is presented as working. `[AI]`
20. **Login is unthrottled and enumerates users by timing.** The rate limiter applies only to public shares (`Program.cs:60-71`). An unknown email returns before PBKDF2 runs (`AuthController.cs:25-26`): about 1 ms versus about 60 ms.
21. **The share password travels in the query string.** `PublicSharesController.cs:15`: the password lands in request logs, proxies and browser history.
22. **No migrations, and the schema is only created in Development.** `DbSeeder.cs:14` `EnsureCreatedAsync` runs only when `IsDevelopment()`. A Production deploy has no schema and no path to evolve one.
23. **Stale thumbnails that are never served.** The key `thumbnail-{nodeId}.png` (`ProcessingWorker.cs:106`) goes through `LocalBlobStorage.SaveAsync`, which **skips existing files** (`LocalBlobStorage.cs:14`), so a new version keeps the old thumbnail. The S3 adapter overwrites, so behavior differs by provider. No endpoint serves thumbnails and `App.tsx` never renders them. `ImageSharp.LoadAsync` on untrusted input has no pixel limit, which is a decompression-bomb risk inside the API process.
24. **Frontend memory.** `sha256(file)` (`api.ts:160-163`) reads the whole file into an ArrayBuffer, so a 4 GB upload crashes the tab. `PreviewPanel` downloads the entire file on selection (`App.tsx:224`) and never revokes object URLs. The token is stored in `localStorage` (`api.ts:58-65`), exposed to any XSS.
25. **Serial worker, no backoff, transient failures shown as "Failed".** `ProcessingWorker.cs:20-23,67-75`: an immediate re-enqueue hot-loops, and `MarkScanFailed` runs on *retryable* errors. (INC-002 is the "fix" that makes it worse.)

## Low / tests / maintainability

26. **Tests don't cover the risky parts.** `[AI]` 6 domain tests (`tests/.../Domain/*`). `Testcontainers.PostgreSql` is referenced but unused (`NetDropbox.Tests.csproj:12`). The test project doesn't reference Infrastructure or Api. There are zero handler, authorization or concurrency tests. CI would prove only that `FileNode` can add a version.
27. **Direct clock and time calls everywhere.** `DateTimeOffset.UtcNow` appears in entities, `ShareService.cs:57` and the janitor, despite `IClock`. Expiry logic can't be tested deterministically.
28. **Client correlation ID trusted verbatim.** `CorrelationIdMiddleware.cs:9-12` accepts any length or content, so log injection is possible. User ID is never enriched into logs, which blocks forensics (see INC-003/005).
29. **Inconsistent error contracts.** Quota exceeded is 409 at start (`StartUpload.cs:39`) but 400 at complete (a `DomainException` via `ExceptionMiddleware.cs:20`). `Pbkdf2PasswordHasher.Verify` `int.Parse` on a corrupt hash throws, giving a 500.

## Answers to the three questions
- **Build:** no. See #1. `git ls-files src/NetDropbox.Infrastructure/Storage` returns nothing, while `DependencyInjection.cs` names those types.
- **README untrue:** CI green (#1); a working app (#2); "reference counts" (#11); "retry/dead-letter" (it's only a status column; nothing reprocesses or inspects the DLQ); Redis and RabbitMQ in the stack (#6); "previews" of thumbnails (#23); "breadcrumb-ready" (`App.tsx:110` shows a GUID slice).
- **Launch blocker:** #3 and #4 together (quarantine bypass). Scan state must follow the *bytes* (version or blob), not the node. #1 and #2 are "can't ship at all", which is different from "shouldn't ship".
